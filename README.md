# CONNECT

Realtime 1:1 and group chat where people find each other by a **private number** instead of a
phone number. No SMS, no carrier lookup — every account gets a unique 10-digit number at signup,
and you share that number with whoever you want to talk to. Plus 1:1 audio and video calling over
WebRTC, with persisted call history.

```
chat-app/
├── backend/     NestJS 12 + Prisma 7 + Socket.IO  ->  Supabase Postgres
├── frontend/    Next.js 16 + React 19 + Tailwind 4
└── deploy/      Caddy TLS terminator  ->  the app, on one https:// origin
```

> **Calling needs HTTPS.** Browsers expose `navigator.mediaDevices` — the camera and microphone
> APIs every call depends on — only inside a *secure context*. `localhost` counts as secure, so
> calling works in local dev. A plain-HTTP LAN address does **not**, and there
> `navigator.mediaDevices` is `undefined` rather than restricted, so `getUserMedia` cannot be
> called at all. Chat keeps working, which is what makes it quiet. See
> [`deploy/README.md`](deploy/README.md) for the measurements and the fix.

## How the private number works

On registration the backend generates a random 10-digit number and stores it in
`users.connectNumber` behind a unique index.

- Generated by `generateConnectNumber()` — `backend/src/common/utils/connect-number.util.ts`
- Displayed as `3204-5879-76` by `formatConnectNumber()`, but stored undelimited as `3204587976`
- Lookups run through `normalizeConnectNumber()`, so all of these resolve to the same person:

  | You type                | Normalized       |
  | ----------------------- | ---------------- |
  | `4821993017`            | `4821993017`     |
  | `4821-9930-17`          | `4821993017`     |
  | `+4821993017`           | `4821993017`     |
  | `4821 9930 17`          | `4821993017`     |
  | `+48 (21) 9930-17`      | `4821993017`     |

These are **not real phone numbers**. Nothing is ever texted or dialled. The number is purely an
app-level identifier that happens to look familiar. If you want to change the format, edit the
two functions in `connect-number.util.ts` — the database column stays a plain string either way.

The **Connect** page (`/connect`) is the whole flow: paste a number, hit enter, see who it belongs
to, then send a request. Once they accept, you both land in a direct conversation. Requests and
existing connections are managed in `/requests`.

## 1. Configure Supabase

1. Create a project at [supabase.com](https://supabase.com).
2. Open **Project Settings → Database → Connection string**.
3. Grab **two** strings. Supabase shows several, and picking the wrong one is the single most
   common reason migrations fail:

   | Variable        | What to paste                                       | Used for             |
   | --------------- | --------------------------------------------------- | -------------------- |
   | `DATABASE_URL`  | **Transaction pooler**, port `6543`                 | Pooled traffic       |
   | `DIRECT_URL`    | **Session pooler**, port `5432`                     | `prisma migrate`     |

   Use the *Session* pooler (not the Transaction pooler) for `DIRECT_URL`. Prisma needs to run DDL
   and interactive transactions, and Transaction-mode PgBouncer supports neither.

   Append `?sslmode=no-verify` to both — **not** `require`, despite the name. Supabase's pooler
   presents a self-signed certificate, and in node-postgres `sslmode=require` parses to an empty
   `ssl: {}` object, which leaves Node's `rejectUnauthorized` at its default of `true`. Every query
   then fails with `self-signed certificate in certificate chain`. Only `no-verify` sets
   `rejectUnauthorized: false`. Traffic is still encrypted; you are just not checking the cert
   against a CA bundle. See the Troubleshooting entry if you want real verification instead.

   > **Percent-encode your password.** If it contains `@ : / ? # %`, the URL will misparse and
   > you'll get an auth error that looks like a wrong password. For example a password of
   > `hunter2@vector` must be written `hunter2%40vector` in the connection string.

4. Generate two **different** JWT secrets:

   ```bash
   openssl rand -base64 48   # run twice
   ```

5. Set up the backend env file:

   ```bash
   cd backend
   cp .env.example .env
   ```

   Then edit `.env` and paste in the four values from above.

   ```bash
   # backend/.env
   DATABASE_URL="postgresql://postgres.PROJECT_REF:YOUR_PASSWORD@aws-0-REGION.pooler.supabase.com:6543/postgres?pgbouncer=true&sslmode=no-verify"
   DIRECT_URL="postgresql://postgres.PROJECT_REF:YOUR_PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres?sslmode=no-verify"
   JWT_ACCESS_SECRET="<paste first openssl output>"
   JWT_REFRESH_SECRET="<paste second openssl output>"
   CORS_ORIGIN=http://localhost:3000
   ```

6. Set up the frontend env file:

   ```bash
   cd ../frontend
   cp .env.example .env.local
   ```

   ```bash
   # frontend/.env.local
   NEXT_PUBLIC_API_URL=http://localhost:4000
   ```

   This must be reachable **from the browser**, so `localhost` is right for local dev. If you
   deploy the frontend somewhere, set it to your public API origin and add that origin to the
   backend's `CORS_ORIGIN` (comma-separated for several).

> `.env.example` files are placeholders only — no credentials are committed. Both `.env` and
> `.env.local` are gitignored.

## 2. Run the database migration

```bash
cd backend
npm install
npx prisma migrate deploy
```

This applies `backend/prisma/migrations/20260926090000_init/migration.sql` — the full schema,
7 tables and 5 enums, in one transaction. It is idempotent against a fresh database and safe to
re-run. A second migration, `20260926220000_add_calls/`, adds `chat.calls` and its enums on top.

Confirm it landed:

```bash
npx prisma migrate status
npx prisma studio   # optional: browse the tables in your Supabase dashboard
```

`DIRECT_URL` **must** be set or every Prisma command, including `generate`, will fail with a
missing-env error.

### The `chat` schema

The app does **not** use `public`. Every table and enum is created in a dedicated Postgres schema
called `chat`, so this Supabase project can be shared with other applications without name
collisions:

```
public.document_chunks   ->  whatever else lives in this project
chat.users               ->  this app
chat.messages            ->  this app
...
```

`prisma/schema.prisma` declares `schemas = ["chat"]`, and every one of the 8 models and 7 enums
carries an explicit `@@schema("chat")`. Note that `@@schema` goes **inside the enum braces**, not
after the closing brace — and it is required on enums at all in Prisma's multi-schema mode, since
it is not inferred from the models that use them.

The migration also runs with `search_path=chat,public` pinned on the connection pool
(`src/prisma/prisma.service.ts`), so hand-written `$queryRaw` and any future ad-hoc SQL resolve
against `chat` without needing to be qualified. The one raw query in the codebase is qualified
anyway, belt and braces.

**If `migrate deploy` fails with `P3005: The database schema is not empty`**, that means the
project already has objects in it — usually another app. That is exactly why the `chat` schema
exists, and it is handled: apply the DDL, then record it.

```bash
psql "$DIRECT_URL" -v ON_ERROR_STOP=1 -f prisma/migrations/20260926090000_init/migration.sql
npx prisma migrate resolve --applied 20260926090000_init
npx prisma migrate status     # -> Database schema is up to date!
```

This is the honest version of baselining: the SQL genuinely runs, and only then is the migration
marked applied. Do **not** run `migrate resolve --applied` on its own — that would tell Prisma a
migration happened when no tables were created, and every later `migrate dev` would report
phantom drift.

## 5. Serve it over HTTPS

Calling does not work over plain HTTP on anything other than `localhost`, for the reason in the
callout at the top: the browser never exposes `navigator.mediaDevices` on an insecure origin. So
the supported way to use this on a network is behind TLS, which `deploy/` sets up.

```bash
# From the repository root. Each server is restarted in the background, so
# start them in any order and none of these blocks the next.
(cd backend && ./scripts/restart-api.sh)     # API on 0.0.0.0:4000
(cd backend && ./scripts/restart-web.sh)     # Next on 0.0.0.0:3000
./deploy/restart-proxy.sh                    # Caddy on 0.0.0.0:443 and :8080
```

Then open **`https://192.168.1.46`**. `deploy/README.md` covers the one-time certificate warning,
how to remove it by installing Caddy's CA, and the two settings that are easy to get wrong.

If someone types `http://192.168.1.46:3000` instead, that address now redirects itself to the HTTPS
origin rather than serving a page whose call buttons are permanently dead. See
[Port 3000 corrects itself](#port-3000-corrects-itself).

**Backend** — in `backend/.env`:

```bash
HOST=0.0.0.0
CORS_ORIGIN=https://192.168.1.46,http://localhost:3000,http://127.0.0.1:3000,http://192.168.1.*:3000
```

**Frontend** — in `frontend/.env.local`, switch to same-origin mode:

```bash
NEXT_PUBLIC_API_URL=/api
NEXT_PUBLIC_API_ORIGIN=http://127.0.0.1:4000
HTTPS_ORIGIN=https://192.168.1.46
```

A leading slash is the whole signal. `getApiBaseUrl()` in `frontend/lib/api.ts` reads it as "make
every request relative to the page" rather than "talk to this absolute origin".

Why that is the right choice behind the terminator, rather than a stylistic one:

- **CORS stops applying entirely**, so the API's port 4000 never has to be reachable from a
  browser. Only 443 needs to be open.
- **An `https://` page may not make plain-HTTP requests.** A second origin on port 4000 is blocked
  as mixed content no matter what CORS headers say, so the "point the client straight at the API"
  approach cannot work over TLS.

### One origin, but the socket needs its own rule

REST and the WebSocket do **not** always share a target, and the reason is a hard limitation rather
than a preference: **Next's rewrite proxy does not handle the HTTP `upgrade` event.** A `ws://`
request to a rewritten `/socket.io` path is not proxied at all — measured against `next start`, the
handshake never completes and the client sits on `Reconnecting`. So `getSocketUrl()` branches on the
page's scheme, and both branches are forced:

| Page scheme | Socket target                     | Why                                                   |
| ----------- | --------------------------------- | ----------------------------------------------------- |
| `https://`  | the page's own origin             | An https page may not open an insecure WebSocket, and Caddy *does* handle the upgrade |
| `http://`   | the API on port 4000, directly    | Next cannot proxy the upgrade, so the alternative simply does not connect |

Both are verified in the test suite — the `localhost` suite asserts live delivery, the HTTPS suite
asserts the socket reports `Live` and that no request left the serving origin.

There is a second sharp edge in `next.config.ts` on the same path, which is easy to miss: Socket.IO
handshakes on `/socket.io/` **with a trailing slash**, and that is the only form the API answers
on. With Next's default `trailingSlash: false`, the request is normalised to `/socket.io` and the
API 404s. The rewrite therefore lives in the `beforeFiles` phase, which runs ahead of that
normalisation and proxies the request with its slash intact.

### Port 3000 corrects itself

Next still has to listen on `0.0.0.0:3000` for Caddy to reach it, so `http://192.168.1.46:3000`
stays reachable from the LAN. It cannot be bound to loopback instead — Caddy reaches the host over
the Docker bridge at `172.17.0.1`, and a service bound to `127.0.0.1` is not reachable from there
(measured: connection refused).

Left alone, that port is the exact trap this section exists to prevent. Chat works, so nothing looks
wrong, and the call buttons are dead because that origin has no `navigator.mediaDevices` at all.
So `frontend/proxy.ts` answers it with a **308** to `HTTPS_ORIGIN`, keeping path, query, method and
body. Typing the plain-HTTP address now lands on `https://192.168.1.46`, where calling works.

It is gated so it cannot break the cases that must keep working:

| Condition                        | Behaviour                              | Why                                                             |
| -------------------------------- | -------------------------------------- | --------------------------------------------------------------- |
| `HTTPS_ORIGIN` unset             | no redirect, unchanged behaviour       | `npm run dev` and the plain-HTTP LAN mode have no HTTPS origin to send anyone to |
| `X-Connect-Proxy` present        | served normally                        | already arrived through Caddy, so it *is* the secure origin; redirecting would loop |
| hostname is loopback             | served normally                        | `localhost` is already a secure context, and the dev server has no TLS listener |

Caddy sets that header in `deploy/Caddyfile`. One consequence worth knowing: the hop changes origin,
and browsers strip the `Authorization` header on a cross-origin redirect, so a token-bearing request
aimed at port 3000 arrives unauthenticated. The app never does this — it calls `/api` relative to the
page, which by then is already on HTTPS.

Measured behaviour of every branch:

| Request                                      | Response                                       |
| -------------------------------------------- | ---------------------------------------------- |
| `GET http://192.168.1.46:3000/chats`         | `308` → `https://192.168.1.46/chats`           |
| `POST http://192.168.1.46:3000/api/…`        | `308`, method and body preserved               |
| `GET https://192.168.1.46/chats` (via Caddy) | `200`, no redirect                             |
| `GET http://localhost:3000/`                 | `200`, no redirect                             |

## 6. Access it from your LAN

`restart-proxy.sh` already binds everything to `0.0.0.0`, so there is nothing further to configure.
Find your address with `ip -4 -o addr show scope global` and share **`https://<your-lan-ip>`**.

The certificate is issued for one specific address, currently `192.168.1.46`, set in two places:

```bash
# deploy/Caddyfile
https://192.168.1.46 { ... }

# deploy/restart-proxy.sh
SITE_ADDRESS="192.168.1.46"
```

`restart-proxy.sh` refuses to start if the two disagree, because a mismatch produces a container
that comes up healthy and serves a certificate for the wrong address. The machine's own hostname is
useless here — `/etc/hosts` maps it to `127.0.1.1`, so no one else on the network can resolve it.

For plain-HTTP development on a LAN address — no calling, but chat works — leave the terminator
down and start only the two app servers, with `NEXT_PUBLIC_API_URL` unset so the client derives the
API host at runtime:

```bash
cd backend && ./scripts/restart-api.sh   # 0.0.0.0:4000
cd backend && ./scripts/restart-web.sh   # 0.0.0.0:3000
```

That unset part is the important bit. `NEXT_PUBLIC_*` values are inlined at **build** time, so
hardcoding `http://localhost:4000` would send every visitor to port 4000 of *their own* machine.
With it unset, one build works on `localhost`, on a LAN IP, and on a DNS name without a rebuild.

Two things worth knowing either way:

- **The `*` in `CORS_ORIGIN` is a deliberate wildcard**, and each pattern is anchored. It matches
  any address in that subnet, so a DHCP change does not break CORS for everyone. It still rejects a
  different subnet, scheme, or port, and `http://192.168.1.46:3000.evil.com`.
- **Behind the terminator, port 4000 need not be exposed.** The browser only ever talks to 443.
  In plain-HTTP mode it must be reachable, because the client connects to the API directly.

> **Note on `crypto.randomUUID`.** It only exists in a browser *secure context*. Browsers treat
> `localhost` as secure, which is why this bug is invisible in local dev and appears only on a LAN
> IP. `frontend/lib/uuid.ts` wraps it with a `getRandomValues`-based fallback, so message sending
> works on plain HTTP. If you add code that uses other secure-context-only APIs
> (`crypto.subtle`, for example), guard them the same way — or just serve the app over HTTPS, which
> is what the terminator is for.

## 7. Try it end to end

1. Register at `/register` — you are dropped straight into `/chats`. Your private number card is
   pinned to the foot of the conversation panel (and above the tab bar on a phone).
2. Open a **second, incognito window** and register a second account. Note its different number.
3. In the first window, go to **Connect** and paste the second account's number.
4. Hit enter. You get their name and avatar — send a request.
5. In the second window, open **Requests** → **Incoming** → accept. The tab flips to
   **Connected** and both windows land in the same conversation.
6. Send a message. It appears in the other window with no reload, along with a typing indicator
   while they compose and a `✓✓` seen-by receipt once they read it.
7. Reload. Everything persists, and the conversation is in the list with an unread count.
8. Click **📞** or **🎥** in the chat header. If the terminator is running, the other window gets
   an incoming-call dialog; accept it and you should see each other, with mute, camera and hang-up.
   If the buttons are greyed out, the origin is not secure — see
   [Serve it over HTTPS](#5-serve-it-over-https).
9. Hang up. Open the clock icon in the chat header for the **Call history** popover — each entry
   carries its direction, outcome and duration.

Two devices on the same network can place a real call to each other. Two devices behind separate
routers cannot — see [How calling works](#how-calling-works).

## How calling works

1:1 audio and video over WebRTC, direct peer to peer. The server is a signalling relay and a
bookkeeper; no media passes through it.

### The server is only a relay

Signalling is opaque to the server. SDP offers and answers and ICE candidates are the two
browsers' own private negotiation, so `call:signal` verifies only that the sender is one of the two
parties on that call, then forwards the blob to the other. It never parses the SDP, and the payload
is capped at 20 000 characters so the relay cannot be used as a storage channel.

### Status is derived, never trusted

The client sends `reason: "hangup"`, and the server discards that for anything load-bearing. It
records **who ended the call** and derives the status from that, so a peer cannot report someone
else's hangup. `sanitizeReason` also strips everything outside `[\w\s:.,()-]` and caps the result at
120 characters, so no peer-supplied text can reach the history UI as markup.

```
CallStatus:  RINGING -> ACCEPTED -> ENDED_BY_CALLER | ENDED_BY_CALLEE
             RINGING -> DECLINED | MISSED | FAILED
```

### One account, many devices

A signed-in account is one identity but many **devices** — several tabs, a phone, a laptop — and
the two are not interchangeable. The account is the right unit for *state*: a call should ring
everywhere so it can be picked up wherever the user happens to be. The account is the wrong unit
for *media*: a WebRTC peer connection is negotiated between two specific endpoints.

So the client mints a `deviceId` per tab (`sessionStorage`, so two tabs are two devices and a
reload in the same tab is still the same device) and sends it on every call action, and the
server tracks a **leg** — the two devices actually carrying one call:

```ts
// chat.gateway.ts
interface CallLeg {
  callerDeviceId: string | null;
  callerSocketId: string | null; // null after a restart, until the device re-claims it
  calleeDeviceId: string | null; // null until somebody answers
  calleeSocketId: string | null;
  touchedAt: number;             // TTL pruning, see below
}
```

Socket ids are tracked next to device ids because a reconnect mints a new socket id and a
mid-call reload has to be able to resume. Each socket is explicitly put in a room named after its
own id, which is what makes a single-socket emit possible.

Two rules follow, and the whole design exists to enforce them:

| | Audience | Why |
|---|---|---|
| **State** — `call:accepted`, `call:ended`, `call:outgoing` | every device of **both** users | A ring should reach all of them, so any device can end it. And once one device decides anything, the others have to hear that decision. |
| **Media** — `call:signal` | the **one** socket holding the other end of the leg | An SDP offer or ICE candidate is only meaningful to the peer connection it was generated for. |

Each device then works out which of three things it should do about an accept, by comparing the
device ids the server sent with its own:

- **the calling device** builds a peer connection and offers;
- **the answering device** already has one up and waits for that offer;
- **any other device** is a bystander. It stops ringing, and shows a passive "on your other
  device" note instead of the full call surface — no hang-up button, because hanging up from a tab
  that holds no media would drop a conversation happening on another screen.

The previous code had neither rule. `call:accepted` went only to the caller's room, so the
callee's other devices were never told, and because the row was already `ACCEPTED` the 45-second
missed-call sweep could not rescue them either — they rang **indefinitely**, not for 45 seconds,
until reloaded. `call:signal` was broadcast to the peer's whole room, so every tab ran its own
competing negotiation against the same call.

Three smaller consequences of the same fix:

- **A second accept is refused.** `CallsService.accept` is idempotent by design, so a duplicate
  accept returns success — correct for a retried emit from the tab that already answered, wrong
  for a *different* tab, which would then overwrite the callee end of the leg. The gateway refuses
  a second device explicitly.
- **Disconnect is judged per leg, not per account.** `teardownCallsForSocket` ends the call if the
  socket that dropped was carrying its media, or if it was the account's last socket. Closing a
  bystander tab is harmless; closing the tab that holds the peer connection ends the call even when
  the account is still connected elsewhere, which is what the old "does the user have any socket
  left" rule got wrong.
- **Legs cannot leak.** Entries are dropped when a call is announced as ended, and any leg older
  than two hours is pruned on write — for calls closed outside the gateway entirely, such as a
  missed ring expired by a history read.

### Answering is not connecting

Pressing Accept starts two independent things, and the code used to run them one after the other:
open the camera, **then** tell the server. Answering is a database write on another continent and
media is the local hardware, so doing them in sequence charges the user for the sum instead of the
larger of the two, and — this is the part that mattered — the device reported itself *connected*
while the server had not been told anything.

That ordering is the reported bug wearing a different hat. A call rings on every device; one device
presses Accept; it looks connected immediately; the caller is still hearing ringback; and every
other device keeps ringing until the write finally lands. From the outside that is indistinguishable
from "the answer did not register", and it self-heals eventually, so it reads as flakiness rather
than as a defect. It was not flakiness — it was a slow database, and the UI was lying about which
side of the accept it was on.

So the accept is a three-step sequence, and each step is visible:

| Step | Screen | What it means |
|---|---|---|
| Ask the server | `connecting` | The answer is sent. The call is answered, not yet connected. |
| Server commits, then answers | `connecting` | Other devices stop ringing here, because `call:accepted` goes out on the write. |
| Camera opens | `active` | Media exists and the timer can honestly start. |

The media and the write now **overlap** rather than queue, so the common case is the slower of the
two instead of the sum. The intermediate screen is a real state rather than a spinner over a lie: it
carries a cancel, because a user who pressed Accept and sees nothing happen should be able to undo
it.

Two timeouts bound that wait, and their relationship is the subtle part:

- `ACCEPT_ACK_TIMEOUT_MS` (45s, client) sits **above** the server's own ceiling. It started at 20s,
  which is *inside* the 30s the API will queue for a database connection — so the client tore down
  calls the server had accepted moments later, ending them for both parties. A client deadline below
  the server's worst case does not fail fast; it fails wrongly, and worse than the thing it was
  meant to protect against.
- Exceeding it **ends the call** rather than leaving it hanging. The write may or may not have
  committed, and the only way to find out for sure is to end the call, which resolves both cases and
  tells every device. Leaving it ringing is the one outcome that reproduces the original bug.

This exposed a server-side bug that had been latent the whole time. `WsHttpExceptionFilter` emitted
an `exception` event when a handler threw and returned — but it never called the acknowledgement
callback, because a handler that throws never reaches its `return`, so Nest sends no reply either.
Any client that treated a missing ack as "it did not work" waited out its full timeout, and the call
it had asked about stayed ringing on every other device meanwhile. The filter now answers the ack
with the same message it emits.

### The details that are easy to get wrong

- **Direct conversations only.** `CallsService.start` rejects a group call with `400`. A mesh
  negotiation between N peers is a different protocol, not a parameter.
- **No uniqueness constraint on live calls.** A partial unique index is the obvious way to stop two
  live rows, but it cannot express "one per direction per pair" without also blocking a legitimate
  re-ring. Instead `endStaleCalls()` closes any prior live row before ringing again, so the
  invariant lives in the service rather than in the schema.
- **`peer` is resolved relative to the viewer.** `serializeCall` names the *other* participant, so a
  payload built for the callee has the caller in `peer`. That is correct for its recipient and wrong
  for anyone else — and as soon as a payload is *relayed* the distinction bites. `call:accepted` is
  produced while handling the callee's accept but delivered to the caller, so it is re-serialised
  per recipient with `viewFor()`. Getting this wrong made the incoming dialog tell someone the call
  was from themselves; the E2E suite now asserts both directions of both payloads.
- **ICE candidates are buffered.** A candidate arriving before the remote description is set is
  dropped by some implementations, which surfaces as a call that connects to nothing. `PeerConnection`
  queues them until the description lands.
- **What the tab is showing is one value, not four.** `incomingCall`, `activeCall`, an "elsewhere"
  call, and an `outgoingRinging` boolean were four independent pieces of state, which made "ringing
  and connected at the same time" representable and gave every socket handler a reason to read all
  four. `CallProvider` keeps a single `CallScreen` discriminated union instead: the impossible state
  has no representation, and the handlers can read the current value through a functional update
  instead of being re-registered on every transition. (Re-registering them was not free — it
  dropped and re-added five listeners mid-call, and a `call:signal` landing in that gap was lost
  with no error raised anywhere.)
- **No STUN or TURN.** `ICE_SERVERS` is empty, so peers exchange host candidates only. On a single
  flat LAN that is sufficient and adds no external dependency. Across separate routers or VLANs it
  will not connect, and no client-side setting fixes that — the answer is a TURN server, not a
  WebRTC tweak.
- **Ring timeout is 45 s, handled opportunistically.** There is no background worker. A still-ringing
  call older than the timeout is marked missed when history is read, so a device that went offline
  mid-ring shows up correctly the next time anyone looks.
- **Closing a tab ends the call only if that tab was carrying it.** `teardownCallsForSocket` checks
  whether the dropped socket held a leg, and whether the account has anywhere else to be reached.
  Closing a bystander tab must not drop a call the user is having on another device, and closing
  the tab that holds the peer connection must — otherwise the call sits `ACCEPTED` forever with one
  side talking to nobody.
- **If media cannot start, the call is not built.** `establishPeer` returns `null` with a reason and
  the caller emits `call:end` rather than constructing a connection that could never carry media.
  On an insecure origin `CallMediaNotice` explains why — from capability alone, not from a failed
  call, since the disabled button means there is never a failed call to learn from.

### Talking to a database on another continent

The pool is configured in `prisma.service.ts` and the reasoning is in `prisma/connect-retry.ts`.
Three things there are set by measurement rather than taste, and each replaced a version that
looked reasonable and was not.

| Setting | Value | Why that number |
|---|---|---|
| `CONNECT_TIMEOUT_MS` | 10s | A working handshake to this pooler costs 0.2–0.5s, but the distribution has a long tail: sampling cold connects produced 1.9s and **5.6s** outliers. The original 5s deadline was documented as abandoning "only the attempts that were never going to finish", and measurement refuted it — it was throwing away handshakes that completed at 5.6s. |
| `EXTRA_ATTEMPTS` | 1 | Widening the deadline and keeping three attempts would put a failed acquire back over 30s, which is the one property the retry exists to beat. Two attempts of 10s gives up at ~20s, inside the old single 30s attempt. |
| `min` (warm floor) | 4 | The reason cold connections are the only thing here with a failure mode at all: a query on a pooled connection takes 25–35ms and never touches this code. `min` stops the idle timer dropping below four, and `onModuleInit` opens them at boot so a burst does not discover an empty pool all at once. |

The retry is a `pg.Pool` subclass overriding **only `connect()`**, and that placement is the safety
argument rather than an implementation detail. `Pool.connect()` resolves only once a client is fully
connected, so when it rejects, no query has run and nothing has been written — a retry cannot
double-apply a write, whatever the caller was about to do. A Prisma query extension is one level too
high: there, "the connection dropped" and "the server answered" are the same error, and retrying the
second is how a message gets sent twice.

`test/db/connect-retry.mjs` (11 assertions, `npm run test:db`) pins that argument rather than the
implementation: a blackholed handshake recovers for the price of one deadline, a permanently
blackholed host still surfaces a real error, and five distinct *Postgres* errors — syntax, undefined
table, unknown column, unique violation, not-null violation — each cost exactly one acquire, because
an answer from the server must never be retried.

### The video element is never gated

`VideoSurface` renders its `<video>` unconditionally and shows "No video" as an *overlay*, rather
than conditionally rendering the element. The gated version looks equivalent and is not: the
attaching effect reads `ref.current`, which is `null` on the render where the decision is still
"no video", and since the effect only re-runs when `stream` changes, the element that appears on
the next render never receives the stream at all.

### Media capability is read via `useSyncExternalStore`

`canAccessMedia()` is consulted in one place during render and through `useSyncExternalStore` in
another. Calling it directly during render would be wrong: the server answers "no" (no `navigator`)
and the client's first render answers "yes", so React reports a mismatch on every call button.
`useSyncExternalStore` uses the server snapshot for the hydration render and the real one
immediately after.

## Data model

```
users ──┬──< auth_sessions              (refresh tokens, SHA-256 hashed)
        ├──< connections (requester) ──> (addressee)   PENDING|ACCEPTED|DECLINED|BLOCKED
        ├──< conversation_participants >── conversations ──< messages ──< message_reads
        └──< calls (caller) ──> (callee)
```

| Table                    | Purpose                                                                | Key constraints                                                            |
| ------------------------ | ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `users`                  | Accounts and profiles                                                 | `connectNumber` unique, `email` unique                                    |
| `auth_sessions`          | One row per issued refresh token                                      | `refreshTokenHash` unique; `revokedAt` marks it spent                      |
| `connections`            | Directed friend request, one row per pair                             | `@@unique([requesterId, addresseeId])`                                     |
| `conversations`          | Direct or group                                                       | `directKey` unique — the idempotency guard for 1:1 chats                   |
| `conversation_participants` | Membership + role + mute state + per-conversation last-read pointer  | `@@unique([conversationId, userId])`                                       |
| `messages`               | Message body, edit and soft-delete metadata                           | `@@unique([senderId, clientId])` — the idempotency guard for sends         |
| `message_reads`          | Who has read what                                                      | `@@unique([messageId, userId])`                                            |
| `calls`                  | One row per call attempt: direction, outcome, timings                  | indexed on `(conversationId, startedAt)`; **no** unique index on live rows |

Two details worth calling out, because they remove whole classes of duplicate-data bugs:

- **`directKey`** is the two participant IDs sorted and joined with `:`, so a direct chat is
  identified by its members rather than by a random ID. Asking for a chat with someone you already
  have one with returns the existing conversation instead of opening a second one, with no extra
  locking needed — the unique index absorbs the race.
- **`@@unique([senderId, clientId])`** lets the client generate a UUID per outgoing message and
  retry freely. If the network drops after the server committed, the retry hits the constraint and
  returns the original row rather than posting the message twice.

Enums: `UserStatus` (ACTIVE/SUSPENDED/DELETED), `ConnectionStatus`, `ConversationType`
(DIRECT/GROUP), `ParticipantRole` (OWNER/ADMIN/MEMBER), `MessageType` (TEXT/SYSTEM), `CallStatus`
(RINGING/ACCEPTED/ENDED_BY_CALLER/ENDED_BY_CALLEE/DECLINED/MISSED/FAILED).

## WebSocket reference

Socket.IO, same origin as the API, namespace `/`. Authenticate during the handshake:

```js
const socket = io("http://localhost:4000", {
  auth: { token: accessToken },
});
```

`connection:ready` confirms success; `auth:error` means the token was missing, expired or
invalid, and the socket is closed.

### Client → server

| Event                | Payload                            | Description                        |
| -------------------- | ---------------------------------- | ---------------------------------- |
| `conversation:join`  | `{ conversationId }`               | Verify membership, then join room  |
| `conversation:leave` | `{ conversationId }`               | Leave the room                     |
| `message:send`       | `{ conversationId, clientId, body }`| Persist and broadcast              |
| `message:edit`       | `{ messageId, body }`              | Edit own message                   |
| `message:delete`     | `{ messageId }`                    | Soft-delete own message            |
| `message:read`       | `{ conversationId, messageId }`    | Advance the read pointer           |
| `typing`             | `{ conversationId, isTyping }`     | Ephemeral, never persisted         |
| `call:start`         | `{ conversationId, kind, deviceId }` | Ring the other party; `kind` is `AUDIO` or `VIDEO` |
| `call:accept`        | `{ callId, deviceId }`          | Accept; acks with `{ call, callerDeviceId, calleeDeviceId }`, and a *second* device is refused |
| `call:reject`        | `{ callId, reason?, deviceId }` | Decline a ringing call             |
| `call:end`           | `{ callId, reason?, deviceId }` | Hang up — the actor decides the status |
| `call:cancel`        | `{ callId, reason?, deviceId }` | Withdraw before the other answers  |
| `call:signal`        | `{ callId, type, data, deviceId }` | Relay one SDP or ICE blob to the one device holding the other end of the leg |

Every call action carries the `deviceId` of the tab that sent it (`/^[A-Za-z0-9_-]{8,64}$/`, minted
per tab and kept in `sessionStorage`). It is the only thing that distinguishes one of the same
account's devices from another, and both the accept-collision guard and the signalling route depend
on it. See [One account, many devices](#one-account-many-devices).

`call:signal`'s `type` is `offer`, `answer`, `candidate` or `hangup`, and `data` is a JSON-encoded
**string** rather than a nested object. Modelling the SDP field by field would mean tracking a
shape the server never inspects, and the browser's is large and version-specific; forwarding it
opaque is both simpler and the reason the server can honestly claim not to parse signalling.

### Server → client

| Event              | Description                                            |
| ------------------ | ------------------------------------------------------ |
| `connection:ready` | Your user ID, after a successful handshake             |
| `auth:error`       | The handshake carried no valid token; the socket closes |
| `message:new`      | New message                                             |
| `message:updated`  | An edit                                                |
| `message:deleted`  | A soft-delete — a **separate** event, not `message:updated` |
| `message:read`     | Someone advanced their read pointer                     |
| `typing`           | Someone started or stopped typing                       |
| `presence:update`  | A user came online or went offline                      |
| `call:incoming`    | A call is ringing for you — on every device you have    |
| `call:outgoing`    | Another of your devices placed a call (not sent to the one that did) |
| `call:accepted`    | Answered, with `callerDeviceId` and `calleeDeviceId` so each device knows its role |
| `call:ended`       | The call is over, with the derived status and duration  |
| `call:signal`      | SDP or ICE, delivered to the one device negotiating     |
| `exception`        | Failed request, with the real HTTP status and message   |

`call:accepted` and `call:ended` go to **both** parties, not just the other one. The acting tab
clears its own state from the acknowledgement it already has, but its sibling tabs were showing the
call too and are told by nobody otherwise — a decline on one tab while another kept ringing was the
visible symptom. Redelivery to the acting tab is harmless because its cleanup is idempotent, and
suppressing it would mean every terminal handler had to remember to exempt itself.

A decline is **not** its own event. `call:reject`, `call:end` and `call:cancel` all funnel into
`announceCallEnd()` and emit the same `call:ended`, because the client's response is identical in
each case — close the panel, show the outcome, refresh history. Distinguishing them would mean three
handlers that do the same thing. The reason lives in the payload's status, which the server derived
from who acted, not from the client's word.

Every inbound event is authorised server-side — membership is re-checked on `join`, on every send,
and on every edit or delete. Room membership is a routing optimisation, never the access control.

Three implementation notes:

- **Duplicate delivery.** A user is in both their personal room (`user:<id>`, so a message sent
  while you have the chat closed still reaches you) and each conversation room. Socket.IO would
  happily deliver the same event twice, so `broadcastToConversation` emits to the **union** of
  those rooms via `server.to(rooms)` in a single call rather than looping and emitting separately.
- **WebSocket errors.** Throwing a Nest `HttpException` from a gateway otherwise surfaces to the
  client as an opaque `500`. `WsHttpExceptionFilter` translates it into an `exception` event
  carrying the real status code and message, which is what lets the UI show "You are not a member
  of this conversation" instead of "Unknown error".
- **Call payloads are per-recipient, not relayed.** `call:accepted` is built while handling the
  callee's accept but delivered to the caller, and `peer` means "the other person" from the
  reader's perspective. Emitting one pre-serialised payload to both parties tells each of them they
  are calling themselves. Every call event is therefore re-serialised with `viewFor()` against the
  socket's own user ID — once per party, not once per device, since `peer` is viewer-relative and
  the same payload is correct for every device an account has.
- **Media is addressed to a socket, state to a room.** This is the distinction the whole
  multi-device design rests on, and it is worth stating plainly because the two look similar in
  code: `server.to(userRoom(id))` reaches every device an account has, and
  `server.to(socketId)` reaches exactly one. Using the wrong one is not a cosmetic mistake — a
  broadcast `call:signal` has every extra tab running its own competing negotiation, and an accept
  that only notifies the other party leaves the rest ringing forever.
- **Soft-deletes get their own event.** `message:updated` means an edit. A delete emits
  `message:deleted`, because a client that reconciles a conversation list has different work to do
  for the two — and a tombstone is not the same as edited text.

## Auth model

Short-lived access token, long-lived rotating refresh token, both signed with HS256 and separate
secrets.

- **Access token** — 15 min, kept in a module-scoped variable in `lib/api.ts` and mirrored to
  `localStorage` so a page reload keeps you signed in.
- **Refresh token** — 30 days. The server stores only its **SHA-256 hash** in `auth_sessions`, so a
  database leak does not hand over usable tokens.
- **Rotation with replay rejection** — every refresh stamps `revokedAt` on the presented row and
  issues a new pair. Presenting an already-revoked token returns `401`, so a stolen-and-replayed
  token buys the attacker nothing beyond the one refresh it originally intercepted. The E2E suite
  asserts this.

  Note the scope: rejection is per-token, not per-family. Replaying a spent token does **not**
  revoke the user's other active sessions. If you need family-wide revocation — invalidating
  every device on a suspected theft — the usual approach is a `familyId` column on `auth_sessions`
  and revoking every row sharing the family of the replayed token.
- **Single-flight refresh** — if five requests 401 at once, the client performs exactly one refresh
  and replays the other four with the new token, instead of five racing refreshes where only the
  first would succeed and the rest would log you out.
- **`JwtAuthGuard` is registered as a global `APP_GUARD`**, so new routes are protected by default
  rather than by remembering a decorator. Opt out with `@Public()`. The guard short-circuits for
  non-HTTP contexts, since Passport has no `request.headers` on a WebSocket handshake.

## Tests

The suite is a dependency-free script, not a test-runner harness — it drives a real server and a
real database over HTTP and WebSocket, so it can assert on the actual SQL behaviour (unread counts,
`directKey` idempotency, unique-violation races) that a mocked Prisma client would only pretend to
cover. There is no `jest` config in the project and none is needed.

```bash
cd backend
npm test          # == node test/e2e/run.mjs
```

**133 assertions** against a **live** server and database — no mocks. Start Postgres, `npm run
prisma:migrate`, `npm run start:prod`, and the run will then walk the full lifecycle:

```
register 2 users  ->  assert distinct private numbers
  -> lookup by number in 3 different formats
  -> send / accept / decline / block connection
  -> direct conversation is idempotent (same id on repeat)
  -> group create, add members, role checks (plain member cannot rename)
  -> send, edit, soft-delete, keyset pagination, read receipts, unread counts
  -> Socket.IO: join rooms, receive live, typing, presence
  -> refresh rotation: reuse of an already-revoked token is rejected
  -> validation: bad UUID and unknown body fields both 400
  -> calls: full lifecycle, group refusal, authz, supersede, cancel, payload cap
  -> calls: one account across four sockets — ring everywhere, media to one device
```

The multi-device section is the one that guards the bug this was written for, and it is worth
saying how it is verified rather than merely asserted: reverting the fix makes exactly the
five accept-related assertions fail, with the symptom spelled out (`call:incoming` received,
`call:accepted` never). The other device's event log *is* the diagnosis.

It exits non-zero on the first failure, so it drops straight into CI.

### Cleaning up after a run

Each run registers fresh accounts, so a shared database accumulates throwaway users. The suites
use `@example.com` for exactly this reason — it is reserved by RFC 2606, so it can never collide
with a real signup — and the cleanup script keys off that:

```bash
cd backend
npm run test:cleanup          # dry run, prints what it would remove
npm run test:cleanup -- --yes # actually delete
```

It deletes only `@example.com` users and reports every other account by name without touching it.
There is deliberately no "empty the database" mode: this is a shared Supabase project, and the only
delete that is safe to automate is one scoped to a domain the app owns. Dependent rows go with the
user because every foreign key to `users` is `onDelete: Cascade`; conversations are swept in a
second pass, since they reference users only through their participants and would otherwise be left
as empty shells.

There is no retention job for real messages. Deleting a user's history is a product decision
rather than a technical one, and the schema currently supports it — `Message.deletedAt` is a soft
delete, and a hard delete is `ON DELETE CASCADE` from the conversation — so a retention policy can
be added as a scheduled job without a migration.

There are also browser-level tests that drive isolated Chrome contexts through the real UI and
assert realtime behaviour end to end. Six suites, each measured on the configuration it targets:

| Suite                       | Target                    | Covers                                                                     |
| --------------------------- | ------------------------- | -------------------------------------------------------------------------- |
| UI (localhost)              | `http://localhost:3000`   | 18 assertions: live delivery, typing, seen-by receipts, persistence across a reload |
| LAN HTTPS                   | `https://192.168.1.46`    | 11 assertions: same flows over TLS; asserts no request leaves the serving origin |
| CORS matrix                 | API :4000 direct          | Every allowed origin accepted, near-miss origins rejected                   |
| Calls (browser)             | `https://192.168.1.46`    | 39 assertions: ringing, accept, real peer-to-peer **audio and video**, hang-up, history, teardown |
| Calls (multi-device)        | `https://192.168.1.46`    | 46 assertions over four contexts: one account, several devices — rings everywhere, media reaches exactly one, bystanders carry none |
| Origin gate                 | both                      | 22 assertions across both values of `HTTPS_ORIGIN`: the plain-HTTP URL redirects itself to a working one, and with it unset the notice and disabled buttons still behave |

Two notes on writing these. A browser suite has to wait for hydration before filling a form:
`fill()` writes to the DOM, and if React has not hydrated it overwrites the value with its own
empty state, so the form submits blank and fails native validation with a message that never
reaches the network — invisible to the test, and intermittent because it depends on how fast the
page settles. The call suite verifies the field kept its value instead of assuming it. And the
origin gate exists because the failure it guards is silent by construction: a disabled
button produces no request and no error, so nothing else would notice its absence.

The origin gate spins up its own throwaway `next start` per phase, on a spare port with
`HTTPS_ORIGIN` explicitly set or cleared, and refuses to run on an occupied port. It cannot pass or
fail depending on how the deployment happens to be configured, and it never disturbs the running
app. Note that it is also what proves the redirect preserves a `POST` body, and that authenticated
setup calls have to be aimed at the HTTPS origin: a cross-origin redirect strips `Authorization`,
so a token-bearing request at port 3000 comes back 401.

The call suite is the one worth reading. It uses Chrome's fake capture devices, so it runs headless
on a machine with no camera, and then asserts on the *media itself* rather than on UI state — both
peers report an inbound track with `readyState: "live"`, and the inbound video element reports
non-zero `videoWidth`. A suite that only asserted "the overlay said Connected" would pass against a
connection carrying no media at all.

The multi-device suite is the one worth keeping. It opens four browser contexts, signs two of them
into the same account, and calls from the third while the fourth watches. It then asserts the two
things that were separately broken and separately invisible: that the devices which did *not* answer
stop ringing, and that they hold no media. The interesting part is that this suite was validated by
**reverting the fix** and confirming the specific assertions failed — a suite that never goes red is
not evidence of anything, and this one names the symptom it guards, so a future regression is
legible from the failure output alone.

The HTTPS suite runs with `ignoreHTTPSErrors: true`, which models a user who accepted the
self-signed warning. It also asserts the reverse, that `navigator.mediaDevices` is genuinely
present — that is the property calling depends on, and the reason a certificate error is a calling
bug rather than a cosmetic one.

npm run lint      # eslint
npm run build     # prisma generate + nest build
cd ../frontend
npx tsc --noEmit  # typecheck
npm run build     # production build

## Troubleshooting

**`Error opening a TLS connection: self-signed certificate in certificate chain`**
Your connection string says `sslmode=require`. Change it to `sslmode=no-verify`. Despite the name,
`require` does *not* relax certificate checking in node-postgres — it parses to an empty `ssl: {}`
object, leaving Node's `rejectUnauthorized` at its default of `true`, and Supabase's pooler
presents a self-signed cert. Only `no-verify` sets `rejectUnauthorized: false`.

To get real verification instead, download Supabase's CA cert and pass it explicitly:

```
DIRECT_URL="...?sslmode=verify-full&sslrootcert=/path/to/supabase-ca.crt"
```

**`P3005: The database schema is not empty`**
The Supabase project already contains objects, most likely from another app sharing the project.
This is expected, and it is why the app uses its own `chat` schema. See
[The `chat` schema](#the-chat-schema) for the two-step apply-then-resolve fix. Do not run
`migrate resolve --applied` on its own — that lies to Prisma about what is in the database.

**`Environment variable not found: DIRECT_URL`**
`DIRECT_URL` is missing. `prisma.config.ts` reads it for every command, including `generate`, not
just migrations. Add it to `backend/.env`.

**Auth succeeds via psql but the API returns 500**
Almost always the `sslmode` issue above. `psql` defaults to `sslmode=prefer` and does not verify,
so a working `psql` session proves nothing about what `pg` will do.

**`relation "messages" does not exist`**
Raw SQL is resolving against `public` instead of `chat`. `PrismaService` pins
`search_path=chat,public`; if you added a new `Pool` or connection elsewhere, it needs the same
`options: '-c search_path=chat,public'`. Prisma's own generated SQL is schema-qualified, so this
only ever affects hand-written `$queryRaw`.

**Migrations fail with `prepared statement already exists` or `cannot execute CREATE TABLE in a
read-only transaction`**
You used the Transaction pooler for `DIRECT_URL`. Switch to the **Session** pooler.

**`P1001: Can't reach database server`**
Wrong host or port. The Transaction pooler is on `6543` and the Session pooler on `5432`. Note that
the Transaction pooler cannot run DDL, so it is only ever valid for `DATABASE_URL`.

**`CORS_ORIGIN` errors in the browser console**
`CORS_ORIGIN` in `backend/.env` must exactly match the frontend origin, scheme and port included —
`http://localhost:3000`, not `http://127.0.0.1:3000` or `localhost:3000`. Multiple origins are
comma-separated.

**Socket connects, then immediately disconnects**
The browser cannot reach `NEXT_PUBLIC_API_URL`. Remember it is a *public* env var read at build
time, so change it in `frontend/.env.local` and rebuild. Also check it is not blocked by an ad
blocker or VPN that filters WebSocket upgrades.

**`Cannot read properties of undefined (reading 'authorization')` in the gateway**
The global `JwtAuthGuard` is running against a WebSocket context. It must return early when
`context.getType() !== 'http'`.

**The app works on `localhost` but not from another machine on the LAN**
Two separate problems usually hide here. First, the servers must be bound to `0.0.0.0` — set
`HOST=0.0.0.0` in `backend/.env`, and start the frontend with `--hostname 0.0.0.0` (both
`scripts/restart-*.sh` do this). Second, `NEXT_PUBLIC_API_URL` must not be set to
`http://localhost:4000`, because that value is baked in at build time and points every LAN visitor
at their own machine. Leave it unset so the client derives the host at runtime, or set it to `/api`
and run the terminator. See [Access it from your LAN](#6-access-it-from-your-lan).

**The call buttons are greyed out, or `navigator.mediaDevices` is `undefined`**
The origin is not a secure context, so the browser never exposes the camera and microphone APIs.
`localhost` is secure and plain-HTTP LAN addresses are not. The most common cause is opening
`http://<lan-ip>:3000` — the Next server directly — instead of `https://<lan-ip>`, which is the
terminator's address. The app now says so in a notice rather than leaving a dead button. Fix it by
using the `https://` origin; see [Serve it over HTTPS](#5-serve-it-over-https).

> The notice deliberately does **not** depend on a call failing first. `CallButtons` disables itself
> on an insecure origin, and a disabled button cannot be clicked, so an error-driven notice would
> never appear — the exact case it exists to explain. It renders from capability alone. Its
> Dismiss button tracks the message text rather than a boolean, because `mediaUnsupported` is
> derived from the origin and survives `dismissMediaError`, so a flag would reappear on the next
> render and the button would do nothing.

**Chat and video calls both break the moment TLS is on**
Almost always mixed content. An `https://` page may not issue plain-HTTP requests or open
plain-HTTP WebSockets, no matter what CORS returns. Set `NEXT_PUBLIC_API_URL=/api` so REST is
relative to the page, and let the socket target follow the page's scheme — `getSocketUrl()` in
`frontend/lib/api.ts` already does. Then only port 443 needs to be open.

**`tlsv1 alert internal error` / alert 80 from the terminator**
The Caddyfile is missing the global `default_sni` option. Browsers do not put IP literals in the
SNI extension, so without a fallback name the server has nothing to select a certificate with and
aborts the handshake. Add it to the global block:

```
{
    default_sni 192.168.1.46
}
```

**`GET /api/...` returns 404 behind the terminator**
`handle_path` strips the matched prefix, which is correct for `/api/*` because the API has no
global prefix. If you added `app.setGlobalPrefix()` the two must be reconciled, or the strip will
eat part of the real path.

**The socket connects over HTTPS but every request is `Reconnecting` over `http://`**
This is not a bug, it is Next's rewrite proxy refusing to handle the HTTP `upgrade` event. A
`ws://` request to a rewritten `/socket.io` path simply does not get proxied — which is exactly
why `getSocketUrl()` points plain-HTTP pages straight at port 4000 instead. If you ever see it the
other way round, check that the `beforeFiles` rewrite is still in place; it has to run before Next
normalises `/socket.io/` to `/socket.io`.

**`navigator.mediaDevices` exists, but the call rings and never connects**
On a flat LAN with host candidates only, that points at the network rather than the app. Check
`iceConnectionState` in devtools: `checking` that never reaches `connected` means no candidate pair
was ever formed, and no client-side setting will fix that — the peers are not routable to each
other, so you need a TURN server. Also confirm the two devices are on the same subnet; browsers
will not send local addresses across a router.

**`connectionState` stays `new` even though the call is clearly working**
`RTCPeerConnection.connectionState` is never `"completed"` — that value belongs to
`iceConnectionState`. Use `"connected"`. This one has a habit of reading as a dead call when it is
actually a successful one.

**The call rings on every device and never stops on the ones that did not answer**
This was a real bug, and the reason it is written down is that the symptom points away from the
cause. The 45-second missed-call sweep does not fire, because the row is already `ACCEPTED` — only
`RINGING` rows expire — so the stale dialogs did not clear after 45 seconds, they cleared on reload.
The fix was to emit `call:accepted` to **both** parties rather than only the caller, and to address
`call:signal` to one socket instead of the peer's whole room. If you see this again, check that
`announceCallEnd`/`call:accepted` are emitted per-user-room and not to the "other" party: a handler
that excludes the acting user assumes the acting tab already cleaned up its own state, which is true
of that tab and false of its siblings. See
[One account, many devices](#one-account-many-devices).

**One tab's hang-up ends a call happening on another tab**
The converse failure, and the same distinction. `teardownCallsForSocket` must end the call when the
dropped socket was *carrying* the leg, not merely when the account has no socket left. A bystander
tab closing is harmless and must stay harmless.


**CORS errors only from other machines, not from localhost**
`CORS_ORIGIN` is missing the LAN origin. Add a wildcard for the subnet —
`http://192.168.1.*:3000` — so it survives a DHCP change. Remember the scheme and port have to
match exactly. Behind the terminator the page origin is the bare `https://<ip>` with no port, so
the entry is `https://192.168.1.46` — it will not match if you write it with a trailing slash or a
port.

**`crypto.randomUUID is not a function` in the console, on a LAN IP only**
`crypto.randomUUID` requires a secure context, and browsers only treat `localhost` as one. Use
`uuidv4()` from `frontend/lib/uuid.ts`, which falls back to `crypto.getRandomValues`. Any
secure-context-only API needs the same treatment when served over plain HTTP.

**Everything is slow, but the database log shows every backend `idle`**
The time is being spent in the network path, not in Postgres. Check it from the kernel rather than
from the app:

```sh
nstat -az | grep -E 'TcpRetransSegs|TCPSynRetrans|TCPTimeouts'   # before and after
```

A run that is healthy shows `0` retransmits while idle and a few dozen during a busy test. If the
counters climb steeply *only* under load while `pg_stat_activity` reports every backend
`idle`/`ClientRead`, packets are being dropped in the path and TCP is recovering by retransmission —
a ~20 second recovery time is the giveaway, because that is where the exponential backoff lands. On
this network that has been observed as `+66` retransmits and `+18` TCP timeouts in a single test
run, with a single `GET /calls` taking 74 seconds and still returning 200. It is a WiFi uplink
problem; no application change fixes it, and the pool settings above are what keep the app *correct*
while it happens (0 failed requests across a full suite) rather than what make it fast.

Ping will not show it. Supabase's load balancer does not answer ICMP at all, so 100% packet loss
against `aws-0-*.pooler.supabase.com` is normal and says nothing; the TCP counters are the signal.

**The incoming call dialog says the call is from me**
A call payload is serialised with `peer` meaning "the other participant", so a payload built for
one party is wrong for the other. This happens the moment an event is relayed rather than rebuilt
per recipient. Use `viewFor(callId, viewerId)` for every call event, and remember it is the *user
ID* of the socket you are emitting to, not of the user whose action produced the event.

**Two people already connected still open a second chat**
A `directKey` collision would mean two rows with the same deterministic key, which the unique
index forbids. Check for stale rows predating the index and re-run the migration.

**Two live call rows for the same pair**
There is deliberately no unique index on live calls, since one cannot express "one per direction
per pair" without blocking a legitimate re-ring. The invariant is `endStaleCalls()` closing prior
rows before ringing again. If you see duplicates, the check was bypassed — a call created through
raw SQL or an older build will do it.

**Port already in use**
`ss -lptnH "sport = :4000"` shows the PID holding the port. Change `PORT` in `backend/.env` and
`NEXT_PUBLIC_API_URL` in `frontend/.env.local` together.

> Kill processes by listening port, not by name. `pkill -f 'dist/main'` matches the command line of
> the shell that invoked it and kills your own session. `backend/scripts/restart-api.sh` does this
> correctly.

> `deploy/restart-proxy.sh` is the exception to "no Docker needed". If Caddy will not bind 443,
> something already holds it — check `ss -lptnH "sport = :443"` before assuming a permissions
> problem, since it will not be one.
